# Codex app-server version policy

The supported CLI is `codex-cli 0.153.4`. Other versions are refused until tested. `schemas.json` pins the draft-07 schemas emitted by that CLI's `codex app-server generate-json-schema --experimental` command. The experimental flag matches the transport's initialization. To regenerate the fixtures with the supported executable, run `node lib/agent-backends/codex/internal/generate-schemas.mjs /path/to/codex`. The generator uses a temporary home and refuses any other CLI version.

The selection includes thread list and read responses, account response, thread start and resume, turn start, steer and interrupt, turn and item notifications, and approval and input requests and responses. This candidate adds model/list, skills/list, mcpServerStatus/list, thread/settings/update, thread/fork and thread/compact/start requests and responses, plus the thread/settings/updated notification. Existing selected schemas retain their emitted content. The native MCP startup notification is named `mcpServer/startupStatus/updated`. It is outside this selection because listing status does not require a startup subscription.

The transport validates the JSON-RPC envelope and initialize response. `payloads.ts` compiles the pinned schemas with Ajv strict mode and exposes version-gated validators for selected payloads. Numeric formats observed in the emitted schemas retain the existing format policy. Unobserved formats fail compilation. Validation returns an invalid outcome without including payload data. Missing, changed, or invalid fixtures and version mismatches return an unsupported outcome. Unknown payload methods return an invalid outcome. `version.ts` pins the fixture's SHA-256 digest; update that digest after reviewing regenerated schemas. The schema permits some nullable fields to be absent even though the CLI-generated TypeScript marks them required. Local payload types follow the schema and retain unknown protocol fields at this boundary.

Native reasoning effort is a nonempty string advertised by a model, including `max` and `ultra`. It is independent of Pi ThinkingLevel. Model metadata requires id, model, displayName, description, hidden, isDefault, supportedReasoningEfforts and defaultReasoningEffort. Skills entries require cwd, errors and skills. MCP status entries require name, authStatus, tools, resources and resourceTemplates. These validators cover metadata. They do not read credentials, resource contents or configuration.

The thread/settings/update response is an object with no required fields. Its schema does not require effective settings. The thread/settings/updated notification carries authoritative threadSettings, including required model, modelProvider and cwd, and optional nullable effort. Thread start, resume and fork responses expose required effective model, modelProvider and cwd, with optional nullable reasoningEffort. Compact start acknowledges with an object that has no required fields. Acceptance alone does not prove compaction has completed. Completion and persisted history still need native lifecycle evidence.

Other methods, including thread pagination, MCP startup notifications, tool calls, token refresh and attestation, require their own payload validators before a backend can trust their payloads. Selecting a validator does not enable a product capability or authorize a new transport method.

This Unit 8 fixture and validator selection was integrated after Unit 7b acceptance. Product capabilities remain gated on their implementation and acceptance. Prior native checks used the copied CLI under a protected-home sandbox and a loopback provider. They covered model pagination, requested-cwd skills, settings notification, empty MCP status, next-turn model and effort, fork history, compact completion and restart persistence. They do not prove real-account inference, real MCP, all approval shapes, a CLI version range or shared-process isolation. The candidate does not change transport, projection or journal behavior.

## Command output

A controlled native command printed one line, waited two seconds, then printed another. It ran under the inherited no-touch sandbox with a loopback provider and no account. On the pinned 0.153.4, both the live `item/commandExecution/outputDelta` stream and the persisted `commandExecution.aggregatedOutput` contained only the second line, with `experimentalRawEvents` off and on. With raw events enabled, a raw `function_call_output` item retained both lines.

The identical command against an integrity-verified official 0.167.0 binary persisted both lines in `aggregatedOutput`, while its live `outputDelta` still delivered only the final part. The persisted-history gap is fixed upstream by 0.167.0; live partial output is not closed in either version.

Command approval, completion, exit status and file changes have separate acceptance evidence. On the supported 0.153.4, complete command output and partial output before completion remain NOT VERIFIED, for the event stream and persisted history alike. The adapter keeps the selected native values and does not infer missing text or forward unvalidated raw events.

A future upgrade to 0.167.0 still requires regenerating the pinned schemas, reviewing their diff and repeating the runtime acceptance checks before the backend enables it; the output comparison is not that acceptance. After any upgrade, repeat the multi-part command against both the event stream and persisted history, then check the same native item in the UI after reload. A passing version probe or a completed command is insufficient to close the live-output limit.
